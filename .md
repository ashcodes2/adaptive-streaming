# 🎬 Adaptive Bitrate (ABR) Streaming — Concept & Architecture Notes

> **Main Goal:** Video playback should run continuously without any pauses or unnecessary buffering. If the internet speed drops or fluctuates, the video should not freeze; instead, its quality should automatically scale down (1080p ➔ 720p ➔ 480p ➔ 360p ➔ 240p), and automatically scale back up to HD when the connection recovers.

---

## 📌 1. Project Overview & Simple Example

**Adaptive Bitrate (ABR) Streaming** is a technique where the video player monitors the user's available network speed and playback buffer in real time, dynamically adjusting the video quality to provide the smoothest possible experience.

### 💡 Real-World Example:
* Suppose you are currently watching the video at the **15th second**, but the player has already downloaded content up to the **23rd second**.
* This means you have an **8-second advance buffer** (runway).
* Even if the internet disconnects or becomes extremely slow for the next 5 to 8 seconds, the video will continue playing smoothly up to the 23rd second without stopping!

## 🏗️ 2. High-Level Architecture & End-to-End Flow

The entire project workflow operates in 4 simple steps:

### Step 1: Video Processing & HLS Packaging (FFmpeg)
* We start with a single high-quality raw video file (`input2.mp4`).
* **FFmpeg** converts this video into 5 standard resolutions: `240p`, `360p`, `480p`, `720p`, and `1080p`.
* **HLS** then splits each resolution into small 4-second video chunks (`.ts` segments).
* It generates two types of playlist files:
  - `master.m3u8` : Contains the list of all available resolutions, their bitrates, and paths.
  - `index.m3u8` : Placed inside each resolution folder, listing the sequential 4-second `.ts` segments for that specific quality.

### Step 2: Server / Distribution Layer
* All playlist files (`.m3u8`) and video segments (`.ts`) are stored in the server directory.
* The server functions purely as a **Delivery Service**: whenever the client (browser) requests a playlist or segment file, the server simply returns it.
* **Important:** The server does not make any quality decisions. All decisions are handled entirely on the client side (browser).

### Step 3: Client Player & Custom ABR Engine (React + HLS.js)
* **HLS.js Engine:** Standard desktop browsers cannot natively play `.m3u8` HLS streams (except Safari). HLS.js runs in the background, downloads the playlists and video chunks, and feeds them into the HTML5 `<video>` player.
* **Bandwidth Estimation (Network Speed):** Each time a video chunk finishes downloading, the system measures how many bytes arrived and how many seconds it took. This gives the live download speed in Mbps. To prevent rapid quality flickering, an **EMA (Exponential Moving Average)** formula is applied to maintain a smooth, stable speed estimate.
* **Buffer Runway Check:** The player continuously monitors how many seconds of video are already buffered ahead of the current playback position.
* **Custom ABR Algorithm (Project Brain):** Evaluates both network speed and buffer health to choose the best quality for the next chunk:
  - If bandwidth is strong and buffer is healthy (> 5 seconds) ➔ Request `1080p` or `720p`.
  - If bandwidth drops or buffer is low (< 3 seconds) ➔ Immediately switch down to `360p` or `240p` to prevent freezing.
* Because the decision applies to the *next* segment, the current playback never stutters.

### Step 4: StreamFlow Dashboard (Live Monitoring UI)
* The React frontend features a real-time dashboard displaying key metrics:
  - Current Internet Speed (Mbps)
  - Buffer Runway (Available buffered seconds)
  - Active Quality & Next Segment Quality
  - Total Quality Switches & Buffering Events

## 🧩 3. Core System Components

### 1️⃣ FFmpeg (Video Transcoder)
* **Role:** A multimedia processing tool that transcodes and scales the single master video into multiple standard resolutions.
* **Why It Is Needed:** To have pre-rendered video qualities ready for all types of user internet speeds and screen sizes.
* **Example Command:**
  ```bash
  ffmpeg -i input2.mp4 -vf scale=-2:720 -c:v libx264 -c:a aac output/720p.mp4
  ```

### 2️⃣ HLS Packaging (HTTP Live Streaming)
* **Role:** Slices large video files into 4-second playable `.ts` segments and generates index playlists (`.m3u8`).
* **Advantage:** Users do not have to download an entire 500MB video file before watching. The browser only requests short 4-second chunks on demand.

### 3️⃣ Backend / Static File Server
* The server is a lightweight file host. When the browser requests `720p/segment_005.ts`, the server delivers that file over HTTP. No server-side transcode or bitrate logic is executed here.

### 4️⃣ Custom ABR Algorithm (The Decision Brain)
The algorithm relies on two primary inputs to choose the video quality:

* **1. Bandwidth (Internet Speed Estimation):**
  - Formula:
    $$\text{Throughput} = \frac{\text{Downloaded Bytes} \times 8}{\text{Download Duration (seconds)} \times 1,000,000} \text{ (in Mbps)}$$
  - Uses an asymmetric **EMA** smoothing model: it drops quality quickly when speed falls (to prevent stalls), and waits for stable speed before upgrading quality.
  - Keeps an **80% safety headroom** (`bandwidth * 0.8`) so normal network spikes do not trigger buffering.

* **2. Buffer Runway (Safety Margin):**
  - If buffer > 5 seconds: Safe to maintain or upgrade to HD quality.
  - If buffer < 3 seconds: Critical guardrail triggers, immediately capping quality to 360p or lower so the buffer does not empty.

* **3. Next Segment Rule:**
  - Quality changes only apply to the upcoming segment. Segments already downloaded in memory are played without interruption.

## 📊 4. StreamFlow Dashboard — 9 Core Metrics

The dashboard provides real-time monitoring of 9 essential playback and network indicators:

| # | Metric Card | Technical Name | Description |
| :-: | :--- | :--- | :--- |
| **1** | **Active Quality** | `Active Quality` | The resolution currently being played on screen (e.g., `720p`, `1080p`). |
| **2** | **Last Downloaded Segment** | `Current Quality` | The resolution of the most recently downloaded video chunk. |
| **3** | **Next Segment Recommendation** | `ABR Recommendation` | The quality chosen by the custom ABR algorithm for the next incoming chunk. |
| **4** | **Estimated Bandwidth** | `Internet Speed` | Real-time network download speed measured in `Mbps`. |
| **5** | **Available Buffer** | `Playback Runway` | How many seconds of video are already loaded and ready to play. |
| **6** | **Playback Position** | `Playback Position` | Current timestamp of video playback (in `MM:SS` format). |
| **7** | **Quality Switches** | `Quality Switches` | Total count of quality upgrades or downgrades triggered by network changes. |
| **8** | **Player Status** | `Player Status` | Current player state (`Playing`, `Buffering`, `Paused`, or `Initializing`). |
| **9** | **Buffering Events** | `Buffering Events` | Total number of times playback stalled due to an empty buffer. |

## 🎯 5. Quick Takeaway Summary

* **Slow Internet / Low Buffer:** Quality scales down (1080p ➔ 480p/240p) ➔ Buffering avoided; video keeps playing smoothly.
* **Fast Internet / Healthy Buffer:** Quality scales up (240p ➔ 720p/1080p) ➔ Full HD visual experience automatically restored.
